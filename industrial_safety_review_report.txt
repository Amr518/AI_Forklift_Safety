 §1. EXECUTIVE SUMMARY

This report documents a rigorous industrial-grade code review of the Forklift
AI Safety System deployed at Limitless Future's factory site. The system uses
computer vision (YOLOv8) to detect pedestrians in forklift operating zones and
controls a physical relay module (RM04U) via serial communication to cut
forklift motion when a human is detected inside a defined Region of Interest.

KEY FINDING: The system has ALREADY been partially migrated from file-based
IPC (relay_status.json in the project directory) to tmpfs-based IPC
(/dev/shm/relay_status.json). Both hardware_worker.py (line 41) and
hardware_manager.py (line 41) reference:

tmpfs filesystem that exists entirely in RAM, is accessible to all users,

 §2. ARCHITECTURE OVERVIEW & FILE MAP
================================================================================

The system follows a PRODUCER-CONSUMER pattern:

 ┌──────────────────────┐     /dev/shm/relay_status.json     ┌─────────────────┐
 │   ai_gui_system.py   │ ═══════════════════════════════> │ hardware_worker  │
 │   (PRODUCER)         │    Atomic write via os.replace()  │   .py (CONSUMER) │
 │                      │                                    │                  │
 │ • PyQt5 GUI          │ <═══════════════════════════════  │ • Serial I/O     │
 │ • YOLOv8 Inference   │    Reads hw_status field back     │ • RM04U Protocol │
 │ • hardware_manager   │                                    │ • N1-N4 / F1-F4  │
 │   .py (bridge)       │                                    │ • Delay Timers   │
 └──────────────────────┘                                    └─────────────────┘
         │                                                           │
         │  config.json (ROI, ports, model, timers)                  │
         │  security.json (role passwords)                           │
         │                                                           │
         └────── /dev/ttyUSB0 (RM04U CH340 USB Relay) ──────────────┘

PRODUCER FLOW (ai_gui_system.py → hardware_manager.py):
  1. CameraWorkerThread reads frames from /dev/videoN
  2. YoloDetector.detect_persons() runs inference (imgsz=320)
  3. AlarmSystem.check_boundaries() evaluates ROI intrusion
  4. USBRelayManager.trigger_relay() writes station_N_trigger to JSON
  5. USBRelayManager._write_bridge() atomically replaces JSON file

CONSUMER FLOW (hardware_worker.py):
  1. Polls /dev/shm/relay_status.json every 50ms
  2. Parses station triggers + relay mappings (Dynamic Routing)
  3. Applies non-blocking On-Delay (debounce) and Off-Delay (hold)
  4. Sends 2-byte ASCII command (N1-N4 / F1-F4) via serial

 §3. ROOT CAUSE ANALYSIS — THE "forklift" USER PERMISSION FAILURE
================================================================================

SYMPTOM:
  "[HARDWARE] Safe status write failed for status: ONLINE"
  System enters safe mode and cuts relay output.

ROOT CAUSE CHAIN:
─────────────────

 Step 1: The system was ORIGINALLY designed to use relay_status.json in the
         project directory (/home/limitlessfuture/Desktop/AI_Forklift_Safety/).

 Step 2: A migration to /dev/shm/relay_status.json was performed (visible in
         the current code at hardware_worker.py:41 and hardware_manager.py:41).

 Step 3: The old relay_status.json file still exists in the project directory
         (15 lines, 340 bytes) — this is now a DECOY file that is NOT used by
         the production code paths.

 Step 4: The actual runtime failure occurs at THIS specific call chain:

         hardware_worker.py:476  main() → update_hardware_status("OFFLINE")
         hardware_worker.py:176  update_hardware_status("ONLINE")
           → safe_read_json("/dev/shm/relay_status.json")  ... reads OK
           → safe_write_json("/dev/shm/relay_status.json")  ... FAILS

 Step 5: The WRITE FAILS because:
         (a) /dev/shm/relay_status.json may not exist yet (volatile tmpfs),
         (b) If hardware_manager.py's _ensure_bridge_file() created it first
             under the "limitlessfuture" user, the file is owned by UID 1000.
         (c) The "forklift" user (UID 1001) cannot write to a file owned by
             "limitlessfuture" unless permissions are set to 666.
         (d) The os.chmod(file_path, 0o666) call in safe_write_json() (line 156)
             ALSO fails because only the file OWNER or root can chmod.
         (e) The .tmp file (line 149) is created by "forklift" but os.replace()
             (line 154) fails if the destination is owned by another user
             (on some filesystem configurations).

 Step 6: After 10 retries (100ms total), the function returns False.
         update_hardware_status() prints the observed error message (line 193).

 Step 7: The GUI reads hw_status == "OFFLINE" (because the write never 
         succeeded), enters safe mode, and disengages relays.

RESIDUAL BUG — STALE PROJECT-DIR FILE:
  The file /home/limitlessfuture/Desktop/AI_Forklift_Safety/relay_status.json
  still exists. While the runtime code no longer reads from it, its presence
  creates confusion for operators and engineers debugging the system.

WHY chmod 777 FIXED IT:
  Running `chmod -R 777` on the project directory had NO direct effect on
  /dev/shm/relay_status.json (which is on a separate tmpfs filesystem).
  However, the chmod likely coincided with the start_system.sh script
  executing its lines 14-15:
    touch /dev/shm/relay_status.json 2>/dev/null
    chmod 666 /dev/shm/relay_status.json 2>/dev/null
  This correctly set permissions. The real fix is ensuring this ALWAYS runs
  before either Python process starts.

 §4. RACE CONDITIONS & CONCURRENCY VULNERABILITIES
================================================================================

4.1  READ-MODIFY-WRITE RACES ON /dev/shm/relay_status.json
─────────────────────────────────────────────────────────────

The JSON bridge file is accessed by TWO independent processes:

  PRODUCER (ai_gui_system.py via hardware_manager.py):
    → _read_bridge() → modify dict → _write_bridge()
    → Called on EVERY YOLOv8 inference cycle (~10 Hz per station × 4 stations)
    → Also called by instant_save_timer_config(), toggle_hardware_coil(), etc.

  CONSUMER (hardware_worker.py):
    → safe_read_json() for polling (every 50ms = 20 Hz)
    → update_hardware_status() → safe_read_json() → safe_write_json()
    → Called every ~2 seconds for ONLINE heartbeat (40 ticks × 50ms)

RACE CONDITION SCENARIO:
  T=0.000ms: GUI reads   {"station_1_trigger": 0, "hw_status": "ONLINE", ...}
  T=0.001ms: Worker reads {"station_1_trigger": 0, "hw_status": "ONLINE", ...}
  T=0.002ms: GUI writes   {"station_1_trigger": 1, "hw_status": "ONLINE", ...}
  T=0.003ms: Worker writes {"station_1_trigger": 0, "hw_status": "ONLINE", ...}
  RESULT: GUI's trigger update is LOST. Relay does NOT fire.

  This is a CLASSIC "Lost Update" race condition.

SEVERITY: HIGH
  A lost trigger update means a pedestrian detection event is silently dropped.
  The forklift continues moving when it should have been stopped.
  At 50ms polling intervals, the window for collision is approximately:
    P(race) ≈ (write_duration / poll_interval) × concurrent_writers
    P(race) ≈ (0.5ms / 50ms) × 2 ≈ 2% per cycle
  Over thousands of cycles per hour, a race WILL occur.

MITIGATION ALREADY IN PLACE:
  The code uses os.replace() (atomic rename on POSIX) for writes, which
  prevents TORN READS (partial JSON). However, this does NOT prevent
  LOST UPDATES because the read-modify-write is not atomic as a unit.

MITIGATING FACTORS:
  - The GUI's in-memory latch filter (hardware_manager.py:278) means redundant
    trigger_relay() calls are filtered BEFORE writing to JSON.
  - The worker's hw_status writes are infrequent (every 2 seconds).
  - The retry loops (10 iterations × 10ms) provide crash tolerance but NOT
    concurrency isolation.


4.2  TEMPORAL COUPLING IN start_system.sh
──────────────────────────────────────────

The start script uses a hard-coded `sleep 1` (line 25) between launching
hardware_worker.py and ai_gui_system.py. This creates a STARTUP RACE:

  T=0.0s: hardware_worker.py starts
  T=0.0s: hardware_worker.py calls update_hardware_status("OFFLINE")
          → Creates /dev/shm/relay_status.json if missing (from safe_write_json)
          → File owned by the LAUNCHING USER (critical!)
  T=1.0s: ai_gui_system.py starts
  T=1.0s: USBRelayManager.__init__() calls _ensure_bridge_file()
          → File already exists → skips creation → reads it → writes to it
          → MAY FAIL if user differs from hardware_worker.py's creator

  If the "forklift" user runs start_system.sh:
    - Line 14: `touch /dev/shm/relay_status.json` creates with forklift's UID ✓
    - Line 15: `chmod 666 /dev/shm/relay_status.json` sets world-writable ✓
    - Both processes CAN write ✓

  If start_system.sh is NOT used (manual launch):
    - Whichever process starts first OWNS the file
    - The other process may fail to write

SEVERITY: MEDIUM
  This only affects non-standard launch sequences, but in a factory environment,
  operators may restart individual components.


4.3  config.json CONCURRENT ACCESS
───────────────────────────────────

config.json is read/written by ai_gui_system.py (GUI thread, main process)
for ROI persistence and global settings. It is read by hardware_worker.py
for serial port configuration (get_config_port(), line 55-68).

The writes to config.json are NOT atomic:
  - save_roi() (line 446-450): Direct `json.dump()` without temp-file rename
  - save_global_configurations() (line 1542-1544): Direct `json.dump()`

If hardware_worker.py reads config.json DURING a write, it may encounter:
  - Truncated JSON → json.JSONDecodeError → retry loop catches this
  - Empty file → returns {} → falls back to "/dev/ttyUSB0"

SEVERITY: LOW
  The worker reads config.json only during startup/reconnection, and the
  retry loop (10 attempts × 10ms) provides adequate crash tolerance.
  However, config.json writes should still use atomic rename for robustness.

 §5. MEMORY LEAKS & LATENCY BOTTLENECKS
================================================================================

5.1  QImage BUFFER LIFETIME HAZARD (CRITICAL)
──────────────────────────────────────────────

FILE: ai_gui_system.py, lines 769-773
CODE:
    frame_rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
    h, w, ch = frame_rgb.shape
    qt_image = QImage(frame_rgb.data, w, h, ch * w, QImage.Format_RGB888)
    self.video_label.setPixmap(QPixmap.fromImage(qt_image))

ISSUE:
  QImage created with a raw data pointer does NOT copy the underlying buffer.
  The numpy array `frame_rgb` must remain alive as long as QImage uses it.
  In this specific code path, `frame_rgb` is a local variable in
  on_frame_received() — it goes out of scope when the method returns.

  HOWEVER, QPixmap.fromImage() performs a DEEP COPY of the pixel data into
  Qt's internal storage. Therefore, `frame_rgb` CAN be safely deallocated
  after setPixmap() completes. The QImage itself is also a temporary.

  This is SAFE in the current code because the conversion chain is:
    numpy → QImage (shallow) → QPixmap (deep copy) → setPixmap()
  
  But if any refactoring stores the QImage without converting to QPixmap,
  it becomes a USE-AFTER-FREE vulnerability.

RECOMMENDATION:
  Explicitly copy the data into QImage for defensive safety:
    qt_image = QImage(frame_rgb.data, w, h, ch * w, QImage.Format_RGB888).copy()

SEVERITY: LOW (currently safe, but fragile)


5.2  OpenCV VideoCapture LEAK ON THREAD STOP
─────────────────────────────────────────────

FILE: ai_gui_system.py, lines 496-498
CODE:
    def stop_camera(self):
        if self.camera_thread is not None:
            self.camera_thread.stop()      # Sets running = False
            self.camera_thread = None       # Drops reference immediately

ISSUE:
  CameraWorkerThread.stop() sets self.running = False, but the thread's run()
  loop may be blocked on self.camera.cap.read() (a blocking OpenCV call that
  can take up to 5 seconds on a hung V4L2 device).

  Setting self.camera_thread = None drops the ONLY reference to the QThread.
  If QThread.__del__() is called while the thread is still executing, Qt will
  print "QThread: Destroyed while thread is still running" and may crash.

  Each leaked CameraWorkerThread holds:
    - 1 cv2.VideoCapture object (~50-200 MB of kernel DMA buffers)
    - 1 OS thread (8 MB stack)
    - Associated V4L2 file descriptors

  After multiple Start/Stop cycles, this accumulates rapidly.

RECOMMENDATION:
    def stop_camera(self):
        if self.camera_thread is not None:
            self.camera_thread.stop()
            self.camera_thread.wait(3000)  # Wait up to 3 seconds
            self.camera_thread = None

SEVERITY: HIGH (memory leak + potential crash in production)


5.3  YOLOv8 INFERENCE LATENCY ANALYSIS
───────────────────────────────────────

The inference pipeline runs in the GUI's signal-slot delivery context:
  CameraWorkerThread (worker thread) → frame_ready signal → on_frame_received()

on_frame_received() executes on the MAIN GUI THREAD (Qt's event loop) because
cross-thread signal-slot connections default to Qt.QueuedConnection.

This means:
  - YOLO inference (detector.detect_persons()) blocks the GUI event loop
  - During inference, the GUI is FROZEN (no button presses, no alarm flashing)
  - Typical inference times for YOLOv8n at imgsz=320:
      CPU (Intel i5): ~40-80ms per frame
      CPU (Intel i3): ~100-200ms per frame

MITIGATING FACTORS:
  - Frame skipping (line 651): Only 1 in 3 frames runs inference
  - imgsz=320 (reduced from default 640): ~4× faster inference
  - Results are cached across skipped frames

EFFECTIVE INFERENCE RATE:
  Camera FPS: ~30 (limited by time.sleep(0.03) in CameraWorkerThread)
  Inference FPS: ~10 per station (every 3rd frame)
  4 stations × 10 Hz = 40 inference cycles/second on the SAME GUI thread

  At 80ms per inference: 40 × 80ms = 3,200ms of compute per 1,000ms wall time
  THIS EXCEEDS 100% CPU UTILIZATION ON THE GUI THREAD.

  In practice, Qt's signal queuing prevents true parallelism, so frames will
  be dropped and FPS will degrade to approximately:
    Effective FPS ≈ 1000ms / (80ms + overhead) ≈ 10-12 FPS total (all stations)
    Per-station FPS ≈ 2-3 FPS

WORST-CASE RELAY TRIP LATENCY:
  Detection delay:  3 frames × 33ms = ~100ms (frame skipping)
  Inference:        ~80ms (YOLOv8n at 320px on CPU)
  JSON write:       ~0.5ms (tmpfs atomic replace)
  Worker poll:      ~50ms (worst case: just missed a cycle)
  On-Delay:         0ms (configured as 0.0s in config.json)
  Serial TX:        ~2ms (2 bytes at 9600 baud)
  TOTAL:            ~232ms best case, ~350ms typical

  This is within acceptable limits for forklift safety (<500ms industry norm),
  but is sensitive to CPU load spikes.

SEVERITY: MEDIUM (adequate for current deployment, but not scalable)


5.4  STYLE RECALCULATION IN EVERY FRAME
────────────────────────────────────────

FILE: ai_gui_system.py, lines 758-760
CODE:
    self.style().unpolish(self)
    self.style().polish(self)

This is called on EVERY frame received by EVERY station — potentially 30+
times per second per station. Qt's style polish/unpolish forces a full
cascade recomputation of the widget's CSS styling engine.

RECOMMENDATION:
  Only call unpolish/polish when the warning state actually CHANGES:
    current_warning = "true" if warning else "false"
    if self.property("warning") != current_warning:
        self.setProperty("warning", current_warning)
        self.style().unpolish(self)
        self.style().polish(self)

SEVERITY: MEDIUM (unnecessary CPU overhead, contributes to GUI lag)


5.5  OVERLAY FRAME COPY ON EVERY FRAME
───────────────────────────────────────

FILE: ai_gui_system.py, lines 688-692
CODE:
    overlay = frame.copy()
    cv2.rectangle(overlay, ...)
    cv2.addWeighted(overlay, alpha, frame, 1.0 - alpha, 0, frame)

frame.copy() creates a full 640×480×3 = 921,600 byte allocation on every
frame. With 4 stations at ~30 FPS each, this is:
    921,600 × 30 × 4 = ~105 MB/s of memory allocation throughput

Modern Python garbage collection handles this, but it contributes to
GC pressure and occasional frame drop spikes.

RECOMMENDATION:
  Pre-allocate the overlay buffer once per CameraCardWidget:
    self.overlay_buffer = np.zeros((480, 640, 3), dtype=np.uint8)
  Then reuse:
    np.copyto(self.overlay_buffer, frame)

SEVERITY: LOW (performance optimization, not a safety issue)


5.6  UNBOUNDED AUDIT LOG GROWTH
────────────────────────────────

FILE: ai_gui_system.py, lines 1703-1707
CODE:
    self.log_terminal.addItem(log_item)
    self.log_terminal.scrollToBottom()

SEVERITY: NONE (already properly bounded)

  - Use polkit rules to prevent the forklift user from accessing terminals

 §7. ARCHITECTURAL REMEDIATION — IPC vs. FILE I/O
================================================================================

The current file-based IPC via /dev/shm/relay_status.json is functional but
has inherent limitations for a safety-critical system. Below is a comparative
analysis of alternative IPC mechanisms:

┌───────────────────────┬────────┬────────────┬──────────┬──────────────────────┐
│ IPC Mechanism         │Latency │ Race-Free? │ Multi-   │ Implementation       │
│                       │        │            │ User?    │ Complexity           │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ JSON on /dev/shm      │ ~50μs  │ NO (need   │ YES*     │ ALREADY DONE         │
│ (current)             │        │  flock)    │ (*chmod) │                      │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ Unix Domain Socket    │ ~10μs  │ YES        │ YES      │ MODERATE — requires  │
│ (SOCK_STREAM)         │        │            │          │ server loop + JSON   │
│                       │        │            │          │ message framing      │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ POSIX Shared Memory   │ ~1μs   │ NO (need   │ YES      │ HIGH — requires C    │
│ (shm_open + mmap)     │        │  semaphore)│          │ struct layout + sync │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ Localhost TCP Socket  │ ~50μs  │ YES        │ YES      │ MODERATE — socket    │
│ (127.0.0.1:PORT)      │        │            │          │ server + client      │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ D-Bus                 │ ~100μs │ YES        │ YES      │ HIGH — requires      │
│                       │        │            │          │ service registration │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ Named Pipe (FIFO)     │ ~10μs  │ PARTIAL    │ YES      │ LOW — but            │
│                       │        │            │          │ unidirectional only  │
├───────────────────────┼────────┼────────────┼──────────┼──────────────────────┤
│ JSON on /dev/shm      │ ~50μs  │ YES        │ YES      │ MINIMAL CHANGE       │
│ + fcntl advisory lock │        │            │          │ (recommended)        │
└───────────────────────┴────────┴────────────┴──────────┴──────────────────────┘

RECOMMENDED STRATEGY: DEFENSE-IN-DEPTH (TWO-PHASE)
────────────────────────────────────────────────────

PHASE 1 — IMMEDIATE FIX (< 1 hour of work):
  Keep the current /dev/shm/relay_status.json architecture but add:
  (a) fcntl advisory file locking to prevent lost updates
  (b) Correct /dev/shm file initialization in start_system.sh

PHASE 2 — STRATEGIC UPGRADE (1-2 days of work):

  - Eliminates ALL file permission issues (sockets use filesystem permissions)
  - Provides TRUE bidirectional communication with guaranteed delivery
  - Enables real-time hardware status push (no polling needed)
